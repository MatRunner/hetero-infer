这里比较奇怪的地方在于：增加线程数没有提高prefill的性能，而且decode的性能还劣化了。这样就衍生出两个主要的问题：

1. 每次测试的计算量是一定的，增加线程后，算力应该是提高的，预期prefill性能也是提高的，但是为什么没有变化？
2. decode公认为mem bound，增加线程并不会影响多少性能，但是threads=64时性能最好，增加线程后逐步劣化？

### Q1：prefill性能问题

提高线程数prefill性能不变，从cpu利用率上可以观察到，即使分配了64个线程，占用率是远未达到的，也就是非计算瓶颈，因此增加线程并不改变性能。

可以论证一下这个事情：

先理论计算一下p512需要的理论算力：Qwen3.8-Q4_K_Medium每次激活6B的参数，根据[理论预测性能](./理论预测性能.md), 一次前向计算量为12GFLOPS\*512=6144GFLOPS。按照prefill 77 tps来算，512/77=6.6s，每秒的计算量为6144/6.6=930GFLOPS。

根据perf采集的实际数据，热点中基本都是libcuda.so，由于编译llama.cpp时使用的还是cuda后端，虽然该用例不使用GPU，但是仍然会加载GPU相关的库，导致性能损耗。

内核函数folio_remove_rmap_ptes占比6.85%，排第三。查询后，Folio的作用是把一组连续的物理页作为一个整体来管理，这个函数的作用是接触物理页群（folio）和虚拟页表项（PTE）之间的映射关系。结合模型的业务形态，这个函数占比高应该是因为在真正运行前做kv，激活缓冲区，权重缓存的分配和调度。

vdso占比2.64%，这个函数就比较常见了。主要是把部分内核的只读代码映射到用户空间中，避免频繁调用时的内核切换损耗。结合下面的热点就是clock_gettime，大概率就是bench的计时功能了。

z4寄存器按照32bit分为四组，用于存储z7和z16的乘加结果，每组进行四次乘加；每个cycle可执行两条sdot，也就是一个cycle的计算量是 64 FLOPS；每秒的计算量是185.6GFLOPS（一颗CPU）。使用上面计算出的930GFLOPS / 185.6GFLOPS = 5 颗CPU。显然，实验分配的线程数大大冗余了，即使每颗CPU只有10%的利用率，50颗CPU也满足了，比测试的最小值64还低。

重新设计测试参数，线程数以16为梯度，测试至64.

其实在测试前，已经发现无论是prefill还是decode，多于64线程性能都不怎么样，结合CPU的NUMA架构也是64C为一个NUMA，就可以考虑线程绑核了。

llama-bench的参数中有提供`--cpu-mask`参数进行绑核（当然使用taskset这种命令也可），使用新的测试命令：

```bash
./llama-bench -m <model> -r 3 -ngl 0 -t 1,5,10 -p 512 -n 1
```

测试结果为：


发现即使是thread=1的时候，仍然有相当高的prefill，这个现象进一步说明了cpu上的prefill非计算瓶颈，但是推翻了上面关于计算量的推论。如果offcpu的时间占比过多，调整thread参数并不会影响性能表现，开启过多的线程反而会造成性能损耗。

使用参数`./llama-bench -m <model> -r 3 -ngl 0 -t 1 -p 512 -n 1`进行TOPDOWN分析，由于测试时间短，且topdown的性能采集为打点式，每次采集1s，间隔1s，采样点中存在典型的mem bound特征如下：

```text
frontend_bound 2.39%
bad_spec 1.39%
retiring 12.02%
backend_bound 84.19%
——mem_bound 59.6%
————l1_bound 57%
```

同时，带宽数据中也有采样点：

```text
rd_ddr_bandwidth_core192 10364MB/S
```

带宽基本只打在线程所在的numa上，单个numa的理论带宽上限为8通道\*4800\*64/8/2numa均分=150GB/s。该采样点距离带宽上限还有不少距离。因此，该用例的mem bound实际上是L1 bound。

采集cache的微观数据：

```text
l1d_bandwidth 95379.66MB/s
l2d_bandwidth 24442.38MB/s
```
l1d的带宽约95GB/s，在众多业务场景中已经算是十分高的值了。询问AI得知一般L1的带宽理论在200~500GB/s之间，而实际业务中能跑出这个性能已经是经过深度优化的代码了。而至于和理论带宽值的gap，可以从[perf数据](../data/perf_p512n1.txt)中看出：

1. load相关的指令（ldr，ld1b）很多，ARM核心如Neoverse V1通常只有2各L/S流水线。汇编片段中有8条load指令，就至少需要4个cycle。按照常理推测呢，L1的最大带宽应该是刚好满足无依赖的连续load的（边界场景），但是由于实际业务中不可能只有load，所以L1的实测带宽是和理论带宽有相当大的gap的。
2. ld1b加载完数据还有解包的过程，吞吐上应该是不及ldr的。
3. 而计算相关的指令，有两条sdot，两条fmla和几条fmul，fcvt（格式转换）。sve向量长度位128b，每次迭代加载（4条ldr h，共8byte，4条ld1b，4\*128b=64byte，共68byte）。而上文中已经推论出计算量是64FLOPs，也就是**计算强度是1**（一个字节计算一次），这个利用率并不高，所以是mem bound。

那么增加线程数后，prefill的性能损耗在哪了？

这里可以发现CPU和GPU的设计区别了，CPU最近一级的L1 cache带宽也只有500GB/s，但是GPU的最近的L1 cache（NV的GPU L1 cache和share mem是一块硬件），带宽能达到数TB/s.

### Q2：decode性能问题

decode的问题是线程从64增加后，tps反而越来约低。这里仍然先进行一下纸面上的分析：通识中本应该是计算瓶颈的prefill都在CPU上表现出了, 那么对于本来就是mem bound的decode阶段，更应该是mem bound了。
