# 基线性能测试与分析

## 摘要

项目目标：在 128 核 ARM 服务器 + 单卡 A100-40G（PCIe）上混合部署 Qwen3.8-Flash-Next（llama.cpp 架构名 `qwen4exp`，UD-Q4_K_XL，103.68 GiB / 176.94B 总参、约 6B 激活、48 层 / 512 专家），寻找显存不足约束下的最佳放置与调优配置。

软硬件栈：2P ARM（2 socket × 64 核，SMT2 共 256 逻辑核，DDR5-4800 2×8 通道，500 GB 内存）× A100-40G PCIe（HBM 1555 GB/s）；引擎为 llama.cpp CUDA 后端。

调优结果（同一配置内比较，明细见文末「最终配置（bench 口径）」）：

| 配置                        | prefill pp512 | decode tg128 | 相对基线    |
| --------------------------- | ------------- | ------------ | ----------- |
| 基线 `-ngl 0 -t 64`         | 77.77         | 6.38         | 1.0× / 1.0× |
| `-ngl 24 -fa 1 -t 64`       | 147.21        | 20.72        | 1.9× / 3.2× |
| `-ngl 999 -ncmoe 999 -t 64` | 101.50        | 26.39        | 1.3× / 4.1× |
| `-ngl 999 -ncmoe 30 -t 64`  | 141.42        | 31.55        | 1.8× / 4.9× |
| `-ngl 999 -ncmoe 28 -t 64`  | 148.42        | 32.25        | 1.9× / 5.1× |
| `-ngl 999 -ncmoe 26 -t 64`  | 157.16        | 33.35        | 2.0× / 5.2× |

结论：**decode 的收益主要来自把 attention/KV 放到 GPU；在显存允许范围内，routed experts 也应尽量放 GPU。prefill 在 `-ngl 0` 时几乎完全被 host→device 搬运支配，专家上 GPU 后最高约 2.0×，但 H2D 仍是每轮固定成本。**

## 正式分析前：CUDA后端和CPU后端的区别

虽然测试使用了cuda后端的llama.cpp，本来整个项目是不涉及cpu后端的，但是在实验过程中，发现**虽然ngl设置为0，但是热点中仍然有明显占比的libcuda.so**，起初我以为是固定开销，便增加了prompt的长度，但是热点的占比基本没变。不过，在ngl=0的情况下，两种后端的性能基本一致的。

**实测后发现，ngl仅控制模型层的放置位置，并不控制计算位置，简单的说，仍然是后端类型决定计算位置**，理解这个含义，能够避免在分析其它参数的时候走弯路。

### Q1：prefill性能问题

提高线程数prefill性能不变，从cpu利用率上可以观察到，即使分配了64个线程，占用率是远未达到的。测试中，观察发现llama-bench进程的cpu利用率也就在1个核多一点，因此即使将-t参数调整到1时，prefill性能不变也不奇怪了。那么奇怪的地方就变成了为什么prefill的性能限制在了一个核上？

topdown信息表明实为core bound。

可以论证一下这个事情：

热点函数中，占比高的是cuda的动态库，这里，仅使用cpu侧的分析技术就有些局限了。

内核函数folio_remove_rmap_ptes的作用，查询后，Folio的作用是把一组连续的物理页作为一个整体来管理，这个函数的作用是解除物理页群（folio）和虚拟页表项（PTE）之间的映射关系。结合模型的业务形态，这个函数占比高应该是因为在真正运行前做kv，激活缓冲区，权重缓存的分配和调度。

vdso这个函数就比较常见了。主要是把部分内核的只读代码映射到用户空间中，避免频繁调用时的内核切换损耗。结合下面的热点就是clock_gettime，大概率就是bench的计时功能了。

看起来只有ggml_vec_dot_q8_0_q8_0这个函数是真正在做计算的，但是占比不高（约4%）。使用CPU的后端采集热点后，该函数的占比飙升到30%+，成为top1热点。计算量是一定的，不会消失，只能转移，既然CPU侧观测不到，那么显然只可能在GPU侧了。

这里，CPU侧的分析基本已经到瓶颈了，而从`nvidia-smi`的信息中，sm利用率基本是吃满的，但是mem占用并不高（约2%）。这个指标就可以说明，上面的分析实际上还是对ngl这个参数没完全理解导致的。ngl仅卸载了模型的层，并不影响计算，实际的计算还是在GPU进行的，所以有GPU频率拉满但是显存占用不高的现象。

根据采集数据，该次 nsys 运行的实际速率约 90 t/s（512 token / 5.6 s），与基线表 77.77 的差异来自计时口径（墙钟 vs bench 的 test_time）与运行批次；这里只使用该次运行的相对量（H2D vs kernel）做归因，绝对 t/s 以基线表为准。kernel 的时间仅有 0.4s 左右（nsys 采集数据支撑），剩余时间在干什么未知。

回到nsys的日志，H2D共124862 MB，64930次，19.27s。平均每次1.9 MB，实际带宽 6.5GB/s。这里原本按 PCIe 4.0 x16 的约 20 GB/s 估算，认为存在 3 倍 gap；但实测 `nvidia-smi` 为 `gen=4, width=4`，`lspci` 显示设备能力 LnkCap 为 x16、链路状态 LnkSta 为 x4（downgraded），即 **A100 实际只跑在 PCIe 4.0 x4 上**：理论带宽约 7.9 GB/s、可用带宽约 6.5~7 GB/s，6.5 GB/s 已经贴近链路上限，**不存在带宽利用率不足**。降速点在插槽/riser/BIOS 配置而非两端设备：GPU 能力为 Gen4 x16，上游端口能力为 Gen5 x16，链路却训练在 Gen4 x4——代际按 GPU 取 Gen4 属正常，宽度掉到 x4 才是异常；95→96 为 root port 直连（无 switch），`dmesg` 也把上限直接归到该端口：`63.012 Gb/s available PCIe bandwidth, limited by 16.0 GT/s PCIe x4 link at 0000:95:00.0 (capable of 252.048 Gb/s with 16.0 GT/s PCIe x16 link)`。若恢复 x16，链路还有约 4 倍余量（x8 对照见文末「PCIe lane 对照」）。也就是说搬运已经跑满，问题不在分片粒度，而在这条链路一次能搬多少。而测试中设置了`-r 3`，19秒的H2D时间，每一轮应该是6s，和测试过程的5.6秒就比较接近了。为了严谨，可以再次采集`-r 1`，`-r 3` 和`-r 5`的nsys特征，为了避免warmup的影响，查看线性度：

| r   | H2D duration/s | H2D size/MB | count | PCIe bandwidth (MB/s) | kernel duration/ms |
| --- | -------------- | ----------- | ----- | --------------------- | ------------------ |
| 1   | 9.6            | 61888       | 32473 | 6447                  | 327                |
| 3   | 19.3           | 124833      | 65036 | 6468                  | 325                |
| 5   | 29.1           | 188720      | 97857 | 6485                  | 328                |

从表格可以发现，size、count、duration 三项均随 r 严格线性，但比例约为 1:2:3，而非 `-r` 名义上的 1:3:5。这个 1:2:3 的比例说明，每次 llama-bench 运行的实际搬运次数是 r+1 次（1 次固定的 warmup 预跑 + r 次正式测试）。因此 H2D 并不是一次性 warmup 或缓存冷启动开销，而是每轮 prefill 都会发生的固定成本；同时三组带宽稳定在 6.4 GB/s 左右（波动 <1%），说明搬运模式不随轮次退化，测量本身干净可复现。

据此可以反解单轮的时间账：r=1 的 9.6s 实际对应 2 次 prefill 搬运，单次 H2D ≈ 4.8s；再加上 kernel ≈ 0.33s，合计约 5.1s，与单轮 prefill 的墙钟 5.6s 基本吻合。前文遗留的 _剩余时间干什么未知_ 的问题由此闭环：剩余时间绝大部分是 H2D 数据搬运，真正的 GPU 计算只占 0.3s 量级。

不过这里又暴露出另一个问题：为什么 kernel 的时间不随 r 累积（三组都稳定在 0.33s），而 H2D 却是线性的？

借助AI帮助分析一下这个问题，学到了新的知识：nsys日志中，CUDA API Summary，使用了 CUDA Graph——`cudaGraphInstantiate` 出现了 1219 次，`cudaGraphLaunch` 出现了 3657 次，而 3657 = 1219 × 3，恰好对应 `-r 3` 时每个 sub-graph 被重放 3 次。

> prefill 的 kernel 计算被捕获固化成 1219 个子图，repeat 阶段靠 `cudaGraphLaunch` 重放；而权重搬运（`cudaMemcpyAsync`）在「图外」，每次真实执行前都独立发起，因此 H2D 能被 nsys 逐次统计、随 r 累积。但图内 kernel 的「重放」执行，nsys 默认不展开统计——kernel event 只在 capture 时记录一次，所以从 `cuda_gpu_kern_sum` 读到的 Total Time 恒等于「单次前向」的计算量（约 0.33s），与 repeat 无关。换句话说，计算每轮都在重放，只是默认的 nsys 报告「看不见」这部分；用 `--cuda-graph-trace=node` 重采即可让 kernel 时间随 r 恢复增长 (实测kernel时间翻4倍到1.28s，包含一次warmup)。这既化解了「kernel 恒定」这个表面矛盾，也提醒观察 CUDA 后端时必须意识到 nsys 对 CUDA Graph 重放的 kernel 存在统计盲区。

因此，**prefill 的瓶颈是 H2D 搬运本身，而这条链路的实际上限只有 PCIe 4.0 x4 的约 6.5 GB/s；搬运已接近上限，要提升 prefill 只能减少需要搬运的字节（把权重留在 GPU），而不是优化分片方式**。

到这里，可以得到一个临时性的结论：对prefill而言，cuda后端的情况下，CPU侧负责调度而不是计算，性能瓶颈是H2D的数据搬运，因此怎样调整线程数都不对bench的性能产生影响。实际生产中，线程数满足不造成调度瓶颈（太少），但是又不会产生太多的锁竞争（太多）即可。

### Q2：decode性能问题

decode的问题是线程从64增加后，tps反而越来越低。

使用nsys采集信息后发现了大问题：prefill阶段计算在GPU，但是decode就在CPU上了（基本无kernel）。行为不统一。确认为调度器的行为：CUDA后端调度prefill计算过程在GPU上进行，但是decode在CPU上进行。（这部分内容会单独整理）且llama-bench有一个参数`-nopo, --no-op-offload`，用于关闭算子卸载，将所有计算都在CPU上进行，默认是`0`，也就是可卸载，将该参数设置为`1`后，prefill的行为就符合预期了。

设定的线程数变多后，热点中libomp，这种线程同步的函数占比明显增加，导致了decode性能损失。同时，spin lock这种自旋锁的占比超过了实际计算的ggml。

可以发现，node 位置对 prefill 影响不大（计算在 GPU，H2D 是 1.9 MB 级的大块搬运，跨 socket 的带宽损失被 H2D 自身 6.4 GB/s 的瓶颈掩盖），而对 decode 影响很大（decode 计算在 CPU，且每 token 伴随大量 host↔device 小包往返）。

### 根因：decode 的小包往返被跨 socket 延迟放大

由 [decode 的 nsys 采集](../data/nsys_d128.log) 可以定量：

- `-ngl 0`、128 个 decode token 共 27,720 次 H2D + 13,860 次 D2H，即**每 token 约 325 次拷贝**；
- 单次仅 13 KB（H2D）/ 25 KB（D2H），每 token 往返各约 2.7 MB；
- 单次 GPU 侧耗时 3.4~4.7 µs、CPU 侧 API 约 9 µs，**耗时由固定延迟主导，带宽利用率极低**。

因此绑定到 GPU 对侧 socket（node 0/1）时，每次拷贝都要多跨一跳 socket，固定延迟成倍上升，128 步累计后 decode 从 13.21 掉到 5.10；而 prefill 的拷贝块大、按 token 摊薄后次数少一个量级，只损失约 7%（94→88）。这也解释了为什么 node 2 与 node 3 之间仍有小幅差异：同 socket 内的两个内存节点，页分配与线程亲和并非完全等价。

**结论：decode 的第一优先级不是线程数，而是把进程与内存绑到 GPU 同 socket（本机实测为 node 2/3）。** 该结论以 `nvidia-smi topo -m` 的 GPU 亲和节点为最终依据，复测时应同时记录 `numactl -H` 的节点距离。

## -ncmoe，--n-cpu-moe

ngl是把模型的layer卸载到GPU上，-ncmoe则是对专家层的精细化调控（从字面上）。由于从源码层面上查看该参数到底有什么行为效率太慢，直接用AI分析给出解释：

> 用「routed experts 腾出来的显存」换「更多整层上卡」
> ncmoe=20会命中`blk.0` ~`blk.19` 中匹配正则
> 只放专家权重，而且只是routed专家
> 和ngl的是反向的，因此两个参数需要联动设置

理解一下，就是把专家层的大部分在CPU上执行。这样就可以腾出显存来放更多的层了。举例来说，如果显存是40，每个层大小是1，原本只能放40层，但是现在把每层的专家sublayer拆出来0.8放在了CPU上，那么每层就是0.2，显存中就能放200层了。

使用下面参数验证：

```bash
numactl -N <node> -m <node> ./llama-bench --numa numactl -m <model> -r 3 -t 64 -p 512 -n 128 -ngl 999 -ncmoe 999
```

如果推论不对，那么测试会显存溢出，但是实测可跑通，且decode性能有巨大提升(20->30)：

```bash
| model                          |       size |     params | backend    | ngl |  n_cpu_moe | threads |            test |                  t/s |
| ------------------------------ | ---------: | ---------: | ---------- | --: | ---------: | ------: | --------------: | -------------------: |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |        999 |      64 |           pp512 |        101.50 ± 6.40 |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |        999 |      64 |           tg128 |         26.39 ± 0.17 |
```

从该手段中理解优化机制：这个参数是把专家层（ffn）的权重计算搬运到了CPU上进行。在上文的分析中，无论是在CPU还是GPU上，都是数据搬运的瓶颈，因此把最制约性能的搬运步骤放在GPU上性价比最高。ffn层的计算对数据的搬运需求是没有attention计算多的。那么显存的分配上尽量先满足attention的计算需求，然后多余的再分配给FFN的计算。

设置ngl 999和ncmoe 999，显存占用约6G（合理，ffn层参数量大），显然GPU的资源还没有利用完全，那么ncmoe的参数调优方向也很明确了：**显存占满预期获得最佳性能**。

为了严谨，按照推论，减少ncmoe的值，预期会带来prefill性能提高，decode性能提高。

## -ctk，-ctv

llama-bench 的 KV 默认类型是 f16，`-ctk/-ctv` 可对 K/V 分别量化以节省显存。使用前有两个硬约束：`-ctv` 量化要求开启 FlashAttention，否则 llama-bench 直接抛异常；q8_0/q4_0 等格式要求 head_dim 能被块大小 32 整除。

为放大 KV 体积，将 `-p/-n` 设为 4096 并开启 verbose 观察缓存体积。

### CPU decode（`-ngl 0`，KV 与 decode 计算都在 host）

| pp4096 | f16  | f16  | 78.83 ± 10.64 | -            | 48         | 48         |
| tg4096 | f16  | f16  | -             | 11.10 ± 0.00 | 48         | 48         |
| pp4096 | q8_0 | f16  | 93.39 ± 0.90  | -            | 25.5       | 48         |
| tg4096 | q8_0 | f16  | -             | 12.24 ± 0.04 | 25.5       | 48         |
| pp4096 | q8_0 | q8_0 | 93.16 ± 0.95  | -            | 25.5       | 25.5       |
| tg4096 | q8_0 | q8_0 | -             | 10.69 ± 0.07 | 25.5       | 25.5       |

**实测结果（CPU decode）：**

- 仅 `-ctk q8_0`：decode 11.10 → 12.24（+10.3%，±0.04；此前一组同口径测量 10.94 → 12.54，+14.6%，方向一致）；
- K/V 同时量化：10.69，比 f16 低 3.7%；
- prefill：78.83 ± 10.64 → 93.39 ± 0.90，f16 组误差 13.5%，已超过 5% 的噪声基线，**不能认定为提升**。

**能下的结论：** 在当前 CPU decode 配置下，若必须量化 KV，只量化 K（q8_0）是唯一观察到可复现收益的设置；同时量化 V 没有收益。

**不能下的结论：** +10.3% 的机制。KV 在 4096 上下文下仅 96 MiB，相对每 token 约 3.75 GB 的权重流量仅约 2.5%，只量化 K 节省的字节不到 1%，**字节减少不足以解释该幅度**。曾怀疑 q8_0 K 改走了整数点积内核，但开启前后 perf 采集到的 CPU 热点函数与占比基本不变，该假设同样缺乏证据；目前无法归因，可能是微架构级访存停顿差异（需看 topdown / LLC-miss 计数），也可能包含运行间偏差。

### GPU 全卸载（`-ngl 999 -ncmoe 28`，KV 与 attention 都在 GPU）

| metric | ctk  | ctv  | prefill       | decode       | k size/MiB | v size/MiB |
| ------ | ---- | ---- | ------------- | ------------ | ---------- | ---------- |
| pp4096 | f16  | f16  | 149.39 ± 1.81 | -            | 48         | 48         |
| tg4096 | f16  | f16  | -             | 16.68 ± 3.41 | 48         | 48         |
| pp4096 | q8_0 | f16  | 144.77 ± 4.13 | -            | 25.5       | 48         |
| tg4096 | q8_0 | f16  | -             | 20.34 ± 2.23 | 25.5       | 48         |
| pp4096 | q8_0 | q8_0 | 144.62 ± 4.99 | -            | 25.5       | 25.5       |
| tg4096 | q8_0 | q8_0 | -             | 20.02 ± 1.81 | 25.5       | 25.5       |

**实测结果（GPU 全卸载）：**

- decode：f16 16.68 ± 3.41 vs `-ctk q8_0` 20.34 ± 2.23，均值差 3.7 t/s，小于两者方差；
- prefill：144.6~149.4，同样落在噪声内。

**能下的结论：** 在当前 GPU 配置下，KV 量化没有可复现的性能收益；不能据此推荐量化，也不能据此断言量化有害。**不能下的结论：** “GPU 上反量化是纯开销”“执行位置决定瓶颈类型”等机理描述目前都只是假设；而且该组数据与 CPU 侧 ±15%~24% 的抖动叠加，无法分离出 GPU 侧效应（该组自身误差约 ±9%~20%）。

**本节可交付的结论只有两条：**

1. 4096 上下文下 KV 仅 96 MiB，相对 103.68 GiB 权重可忽略；KV 量化的价值是**腾显存**（长上下文/多并发时才有意义），不是提升本场景的 t/s。
2. 需要腾显存时，只用 `-ctk q8_0`，不要同时量化 V；GPU 全卸载场景没有观察到收益，不作为默认配置。

## 最终配置（bench 口径）

以下为当前 llama-bench 单流口径下的最优配置；该结果仅用于 bench 对比，不外延到 server/并发场景。

| 配置                       | pp512             | tg128            | 显存   |
| -------------------------- | ----------------- | ---------------- | ------ |
| `-ngl 999 -ncmoe 26 -t 64` | **157.16 ± 1.72** | **33.35 ± 2.30** | ~40 GB |

该行与扫描命令一致（`-p 512 -n 128 -r 3`）；`-fa` 未显式传入（按该版本默认值执行），`-ot "per_layer_token_embd\.weight=CPU"` 也未显式传入（PLE 的驻留位置未显式确认，按显存占用推算不在 GPU）。若换用要求手动指定 PLE 的版本，需补上 `-ot`。

26 已贴近 40G 上限，仅作为 bench 峰值记录；ctx/并发变化会 OOM，不能直接作为 server 配置。

**有效带宽校验：离内存屋顶还有多远**：理论文档的激活权重约 3.75 GB/token（待 gguf 账终裁）是全 host 口径；ncmoe=26 时只有第 0–25 层专家在 host，实际每 token 的 host 读量明显低于该值，因此按 3.75 GB/token 反推的 111–125 GB/s 只能视为**上界**，占单 socket 理论 307 GB/s 的 36–41%。**即使按上界算，最优点也没有把 DRAM 带宽打满**，剩余 gap 主要在逐层串行、host↔device 小包同步与 launch 间隙（ngl=0 的 decode nsys 中 futex 占 67%、每 token 约 325 次拷贝；混合配置的 osrt 同样以 futex 为主）。这修正了“CPU decode 纯带宽受限”的粗结论：带宽指明了方向，延迟与并行度才是当前的主要约束。

**复现信息**：引擎为 llama.cpp CUDA 后端，混合配置数据分别采集自 0.22.0（ngl/fa 组）与 0.28.0（ncmoe/KV 组），两版本热点不可逐项对比；口径统一为 `-p 512 -n 128 -r 3`；NUMA 通过 `numactl -N/-m` 绑定；GPU 实测链路为 PCIe 4.0 x4。版本 commit、CUDA/driver 与编译参数未记录，正式复现前需补齐。

## PCIe lane 对照：x4 vs x8

暂时找不到 x16 的物料，另找了一台同卡、但 CPU 档次更低的环境：PCIe 4.0（16 GT/s）x8，理论带宽约为原环境（x4）的两倍。两次测试均在 NUMA 绑定下进行。

基线 `-ngl 0`：

```bash
| model                          |       size |     params | backend    | ngl |  n_cpu_moe | threads |            test |                  t/s |
| ------------------------------ | ---------: | ---------: | ---------- | --: | ---------: | ------: | --------------: | -------------------: |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       |   0 |          0 |      64 |           pp512 |        159.21 ± 1.29 |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       |   0 |          0 |      64 |           tg128 |         6.85 ± 0.22 |
```

最佳放置 `-ngl 999 -ncmoe 26`：

```bash
| model                          |       size |     params | backend    | ngl |  n_cpu_moe | threads |            test |                  t/s |
| ------------------------------ | ---------: | ---------: | ---------- | --: | ---------: | ------: | --------------: | -------------------: |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |         26 |      64 |           pp512 |        279.88 ± 5.07 |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |         26 |      64 |           tg128 |         30.50 ± 1.21 |
```

与 x4 环境对照：

| 配置            | x4    | x8     | 变化   |
| --------------- | ----- | ------ | ------ |
| `-ngl 0` pp512  | 77.77 | 159.21 | 2.05×  |
| `-ngl 0` tg128  | 6.38  | 6.85   | +7%    |
| `ncmoe=26` pp512 | 157.16 | 279.88 | 1.78× |
| `ncmoe=26` tg128 | 33.35 | 30.50  | −8.5% |

结论：

1. **prefill 基本随链路带宽线性放大**（ngl=0 为 2.05×，ncmoe=26 为 1.78×），H2D 是 prefill 主瓶颈这一判断从 nsys 推断升级为对照实验实锤。
2. **decode 不随链路带宽变化**（6.38→6.85、33.35→30.50），反证 decode 不是 PCIe 带宽受限，而是 CPU 侧计算与延迟受限。
3. ncmoe=26 只有 1.78× 而非 2×，说明 prefill 中仍有非 H2D 部分；新机器 CPU 更弱，host 侧专家计算会拖慢 prefill，因此 1.78× 是链路增益的下界。
4. 两机 CPU 不同，只有 prefill 的倍率可用于验证链路假设；decode 的跨机差异不能直接归因，但“没有随带宽提升”这一事实本身已足够说明问题。

按 x4→x8 的数据粗拟合（每次 prefill 约 18.6 GB 走链路、固定计算约 0.4 s），若该机链路换成 x16，prefill 外推约 450 t/s；该值仅作量级参考，真实收益仍以实测为准。
