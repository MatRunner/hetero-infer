## 正式分析前：CUDA后端和CPU后端的区别

虽然测试使用了cuda后端的llama.cpp，本来整个项目是不涉及cpu后端的，但是在实验过程中，发现**虽然ngl设置为0，但是热点中仍然有明显占比的libcuda.so**，起初我以为是固定开销，便增加了prompt的长度，但是热点的占比基本没变。不过，在ngl=0的情况下，两种后端的性能基本一致的。

**实测后发现，ngl仅控制模型层的放置位置，并不控制计算位置，简单的说，仍然是后端类型决定计算位置**，理解这个含义，能够避免在分析其它参数的时候走弯路。

这里比较奇怪的地方在于：增加线程数没有提高prefill的性能，而且decode的性能还劣化了。这样就衍生出两个主要的问题：

1. 线程数为什么基本不影响prefill的性能？
2. decode公认为mem bound，增加线程并不会影响多少性能，但是threads=64时性能最好，增加线程后逐步劣化？

### Q1：prefill性能问题

提高线程数prefill性能不变，从cpu利用率上可以观察到，即使分配了64个线程，占用率是远未达到的。测试中，观察发现llama-bench进程的cpu利用率也就在1个核多一点，因此即使将-t参数调整到1时，prefill性能不变也不奇怪了。那么奇怪的地方就变成了为什么prefill的性能限制在了一个核上？

topdown信息表明实为core bound。

可以论证一下这个事情：

热点函数中，占比高的是cuda的动态库，这里，仅使用cpu侧的分析技术就有些局限了。

内核函数folio_remove_rmap_ptes的作用，查询后，Folio的作用是把一组连续的物理页作为一个整体来管理，这个函数的作用是解除物理页群（folio）和虚拟页表项（PTE）之间的映射关系。结合模型的业务形态，这个函数占比高应该是因为在真正运行前做kv，激活缓冲区，权重缓存的分配和调度。

vdso这个函数就比较常见了。主要是把部分内核的只读代码映射到用户空间中，避免频繁调用时的内核切换损耗。结合下面的热点就是clock_gettime，大概率就是bench的计时功能了。

看起来只有ggml_vec_dot_q8_0_q8_0这个函数是真正在做计算的，但是占比不高（约4%）。使用CPU的后端采集热点后，该函数的占比飙升到30%+，成为top1热点。计算量是一定的，不会消失，只能转移，既然CPU侧观测不到，那么显然只可能在GPU侧了。

这里，CPU侧的分析基本已经到瓶颈了，而从`nvidia-smi`的信息中，sm利用率基本是吃满的，但是mem占用并不高（约2%）。这个指标就可以说明，上面的分析实际上还是对ngl这个参数没完全理解导致的。ngl仅卸载了模型的层，并不影响计算，实际的计算还是在GPU进行的，所以有GPU频率拉满但是显存占用不高的现象。

CUDA GPU Kernel Summary 中，热点在进行矩阵乘和topK的计算，完全符合MoE模型的prefill的执行。

CUDA GPU MemOps Summary 中，MemOps主要进行的是Host-to-Device的MemCpy。显然是在做权重的搬运。

根据采集数据，512token/90tps=5.6s，测试过程经过了5.6s。但是kernel的时间仅有0.4s左右（nsys采集数据支撑），但是剩余的时间在干什么未知。因为nsys的数据中是没法把osrt的时间和cuda api的时间相加的。

根据nsys的日志，H2D共124862 MB，64930次，19.27s。平均每次1.9 MB，实际带宽 6.5GB/s，而PCIe4.0的GPU通信带宽理论上应该达到20GB/s，存在3倍的gap。也就是负载形态上是小分片的数据搬运（算一片搬运一片？如果按照理论的20GB/s，两秒钟就能把显存的数据换一遍似乎又不合理）。而测试中设置了`-r 3`，19秒的H2D时间，每一轮应该是6s，和测试过程的5.6秒就比较接近了。因此，**prefill瓶颈应该是H2D小分片搬运数据导致PCIe带宽利用率不足**。

nsys cli并不具备timeline的功能，需要借助GUI，该问题暂且搁置，但是最合理的方向，大部分时间应该是H2D的时间损耗。

到这里，可以得到一个临时性的结论：对prefill而言，cuda后端的情况下，CPU侧负责调度而不是计算，性能瓶颈是H2D的数据搬运，因此怎样调整线程数都不对bench的性能产生影响。实际生产中，线程数满足不造成调度瓶颈（太少），但是又不会产生太多的锁竞争（太多）即可。

### Q2：decode性能问题

decode的问题是线程从64增加后，tps反而越来越低。

使用nsys采集信息后发现了大问题：prefill阶段计算在GPU，但是decode就在CPU上了（基本无kernel）。行为不统一。确认为调度器的行为：CUDA后端调度prefill计算过程在GPU上进行，但是decode在CPU上进行。（这部分内容会单独整理）且llama-bench有一个参数`-nopo, --no-op-offload`，用于关闭算子卸载，将所有计算都在CPU上进行，默认是`0`，也就是可卸载，将该参数设置为`1`后，prefill的行为就符合预期了。

设定的线程数变多后，热点中libomp，这种线程同步的函数占比明显增加，导致了decode性能损失。同时，spin lock这种自旋锁的占比超过了实际计算的ggml。

## -fa，开启flashattn

在进行测试前，理解flashattn的机制后，可以知道它的优化本质是减少了数据和显存之间的搬运，由于本次测试，可以说一半权重在GPU上，一半在CPU上。但是CPU上fa是否也生效其实是存疑的。

llama-bench的-fa默认是auto，手动设置为on和off进行测试：fa=on时，性能有些许提升：

## -ncmoe，--n-cpu-moe

ngl是把模型的layer卸载到GPU上，-ncmoe则是对专家层的精细化调控（从字面上）。由于从源码层面上查看该参数到底有什么行为效率太慢，直接用AI分析给出解释：

> 用「routed experts 腾出来的显存」换「更多整层上卡」
> ncmoe=20会命中`blk.0` ~`blk.19` 中匹配正则
> 只放专家权重，而且只是routed专家
> 和ngl的是反向的，因此两个参数需要联动设置

理解一下，就是把专家层的大部分在CPU上执行。这样就可以腾出显存来放更多的层了。举例来说，如果显存是40，每个层大小是1，原本只能放40层，但是现在把每层的专家sublayer拆出来0.8放在了CPU上，那么每层就是0.2，显存中就能放200层了。

使用下面参数验证：

```bash
numactl -N <node> ./llama-bench --numa numactl -m <model> -r 3 -t 64 -p 512 -n 128 -ngl 999 -ncmoe 999
```

如果推论不对，那么测试会显存溢出，但是实测可跑通，且decode性能有巨大提升(20->30)：

```bash
| model                          |       size |     params | backend    | ngl |  n_cpu_moe | threads |            test |                  t/s |
| ------------------------------ | ---------: | ---------: | ---------- | --: | ---------: | ------: | --------------: | -------------------: |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |        999 |      64 |           pp512 |        110.80 ± 1.01 |
| qwen4exp A3B Q4_K - Medium     | 103.68 GiB |   176.94 B | CUDA       | 999 |        999 |      64 |           tg128 |         30.12 ± 0.08 |
```

从该手段中理解优化机制：这个参数是把专家层（ffn）的权重计算搬运到了CPU上进行。在上文的分析中，无论是在CPU还是GPU上，都是数据搬运的瓶颈，因此把最制约性能的搬运步骤放在GPU上性价比最高。ffn层的计算对数据的搬运需求是没有attention计算多的。但是同样伴随着代价，prefill阶段计算任务繁重，而CPU上只能执行向量乘法，所以会有性能损失，130->110损失了约15%的性能。

设置ngl 999和ncmoe 999，显存占用约6G（合理，ffn层参数量大），显然GPU的资源还没有利用完全，那么ncmoe的参数调优方向也很明确了：**显存占满预期获得最佳性能**。

为了严谨，按照推论，减少ncmoe的值，预期会带来prefill性能提高，decode性能下降，还有显存溢出的问题。

## -ctk，-ctv

llama-bench的测试场景中，kv的默认type是f16。可以开启kv的量化来节省显存。但是由于我们的测试场景中，-p和-n设置的都不高，预期该参数并不会产生较大影响。

实际的测试过程中，prefill的性能相比比较稳定，但是decode的性能波动较大，有其它未知因素的影响掩盖了kv量化的影响，不能验证该参数对性能的影响。
