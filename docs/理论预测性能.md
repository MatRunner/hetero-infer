# 理论预测性能

## 环境信息

| 项 | 值 |
| --- | --- |
| GPU | A100 40GB PCIe（GA100，HBM 1555 GB/s，BF16 312 TFLOPS） |
| Host | ARM 服务器，500GB 系统内存，DDR5-4800 2P×8ch（理论 307 GB/s/节点，614 GB/s 聚合）；CPU 2.9 GHz × 2×128-bit FMA/cycle（FP32 16 FLOP/cycle/核），128 物理核，~5.9 TFLOPS FP32 |
| 模型 | Qwen3.8-Flash-Next（qwen4exp）UD-Q4_K_XL，110GB，~175B 总参（逐层账见下文，待 D1 gguf-dump 终裁）/ ~6B 激活，48 层 / 512 专家，含 51B 参数 PLE n-gram 表（Q4 下 ~27GB） |
| 引擎 | llama.cpp（已构建，支持 qwen4exp） |

### CPU 算力口径（ISA 细节，5.9 TFLOPS 的依据）

量化只是压缩了权重，实际在计算的时候还是会反量化回硬件支持的计算精度（一般是FP16，N卡上支持，但是cpu上的指令集是否支持需要看情况而定）。

NEON（ARMv8-A ASIMD，128-bit）的乘加家族不止 FP32，各类型吞吐（相对基准 `FMLA.4S` 的 8 FLOP/条）：

| 类型 | 指令形态 | FLOP/条 | 相对 FP32 | 前提扩展 |
| --- | --- | --- | --- | --- |
| FP32 | `FMLA.4S` | 8 | 1× | 基线（v8.0） |
| FP64 | `FMLA.2D` | 4 | 0.5× | 基线 |
| FP16 | `FMLA.8H` | 16 | 2× | v8.2-A（v8.0 仅有 FCVT，无 native 算术） |
| BF16 | `BFDOT`/`BFMLAL`（无朴素 FMLA 形态） | 16 | 2× | v8.6-A `bf16` |
| int8 | `SDOT/UDOT`（4×4 dot） | 32 乘加 | 4× | v8.2-A `dotprod` |

*实际使用了什么指令，可以在实际测试过程中使用perf采集*

- **本项目按 FP32 FMLA 口径计算力**：UD-Q4_K_XL 属 K-quant 系，ggml 的 Q4_K×Q8_K 内核为 dequant → FP32 FMA——FP16/BF16 路径（服务于 f16/bf16 存储的模型）不会被激活，5.9 TFLOPS 维持
- SVE 的向量长度是实现决定的（128/256/…，非"最大 128"）；即便核有 SVE-256，ggml CPU 后端主路径仍是 NEON，有效算力按 128-bit 口径
- **dotprod 例外**：部分量化组合（如 Q4_0×Q8_0）有 SDOT 内核，但需构建时 `-march` 含 `+dotprod` 才被激活——D1 检查服务器构建的 CFLAGS；保守构建 = 白丢吞吐，属 gap_实现 潜在项

## 预测性能

### 基线预估（B0：纯 host，-ngl 0）

**prefill**：每次前向激活 ~6B 参数（top-k 专家 + 全部 attention；PLE 为稀疏查表，FLOP 可忽略），计算量 2×6B ≈ **12 GFLOP/token**。

关键修正：**Q4 量化不提升 CPU 算力**。llama.cpp CPU 后道对 Q4_K 的路径是 dequant → FP32 FMA——量化节省的是**内存带宽**（decode 受益），prefill 是算力约束形态，不受益。CPU 峰值即 5.9 TFLOPS：

```
prefill 上限 = 5.9 TFLOPS × MFU ÷ 12 GFLOP/token = 492 tok/s @100% MFU
```

ggml CPU GEMM 现实 MFU 约 30~50% → B0 prefill 预期 **150~250 tok/s**。

**decode**：带宽约束形态，每 token 读取全部激活权重 6B×~5bit ≈ **3.75 GB/token**（KV/GDN 状态与 PLE 查表在 512 seq 下占比小，忽略）。

聚合带宽 614 GB/s 不可直接打八折使用：2P interleaved 下约半数访问走远端（延迟 ~2×），叠加 48 层串行同步开销，聚合利用率经验 50~65%：

- 聚合 ×0.6 ≈ 370 GB/s → ~98 tok/s（上界口径）
- 单节点绑定 307×0.75 ≈ 230 GB/s → ~61 tok/s（NUMA 锚点）
- DGX Spark 同模型 25 tok/s（273 GB/s 机器，有效利用率仅 34%）→ 类比本机 55~80 tok/s

B0 decode 预期 **55~100 tok/s**（绝对上界 128）。

### ngl 上限

40G 放不下 110GB，混合部署必需。**PLE（~27GB）是独立张量，不参与 ngl 层切分**——恒用 `-ot per_layer_token_embd\.weight=CPU` 固定在 host。

架构上 3 层 GDN 配 1 层 QSA 重复，每层含 MoE + attn sublayer：

- MoE：路由 (2560,512)=1.31M；每专家 3×2560×640=4.9M × 512 专家 + 共享专家 4.9M → **2.52B/层**，48 层共 121B
- attn：36 层 GDN（58M）+ 12 层 QSA（36M）= 2.5B
- 加 PLE 51B → 总参 **~174.5B**

⚠️ 参数账矛盾：旧口径 131B 总参 × 5bit = 82GB，与 110GB 文件不符；本逐层账 174.5B × ~5bit ≈ 109GB 吻合。**以本账为准，D1 用 gguf-dump tensor 清单终裁后回写全部文档。**

一层 decoder ≈ 2.58B 参数，两种口径：

| 口径 | 每层体积 | 卸载上限（可用 ~36GB = 40 − CUDA context/buffer/KV） |
| --- | --- | --- |
| 文件口径：(110−27)/48 | 1.73 GB/层 | **20~21 层**（保守，已含 attn 高 bit 量化） |
| 参数口径：2.58B×4.5~5bit | 1.45~1.6 GB/层 | 22~24 层 |

取保守值：**ngl 顶格 ~20-21 层，剩余 ~27 层锁在 host**。D1 tensor 清单定准后收敛（影响 ngl 粗扫上限与 gap_物理 的量化）。

### 混合部署预测（主问题：B0 之外能到哪）

**prefill（ngl≈21）**：算力主体虽在 GPU，但各层串行相加，CPU 段主导——

- GPU 段 21/48×12 = 5.25 GFLOP @ 312T×MFU(30~50%) ≈ 0.03~0.06 ms/token（可忽略）
- CPU 段 27/48×12 = 6.75 GFLOP @ 5.9T×MFU(30~50%) ≈ 2.3~3.8 ms/token（主导）
- 合计 ≈ B0 的 48/27 倍 → **270~450 tok/s**。prefill 提升有限，瓶颈仍是 host 剩余层的算力

**decode（ngl≈21，U_machine 粗估）**：

- GPU 段 21/48×3.75 = 1.64GB @ 1555 GB/s ≈ 1.1 ms/token
- host 段 27/48×3.75 = 2.11GB @ 250~370 GB/s（单节点~聚合乐观）≈ 5.7~8.4 ms/token（主导）
- 合计 6.8~9.5 ms → **105~150 tok/s**（未计 launch 间隙；48 层 × ~20 kernel × 3µs ≈ 2.9ms 潜在间隙若不与计算重叠，压向 100 以下——待 nsys 裁决）

对比：B0 55~100 → 顶格 ~105~150，收益约 1.5×；距全 GPU 的 U_ideal 430 仍差 ~3×——**剩余 ~27 层锁在 host 是 40G 显存下的不可消除项（gap_物理 主体）**，这正是本项目要量化的核心结论。

**MTP 投机解码（后置，超出现有三手段）**：一次权重读取验证多 token，摊薄 3.75GB/token——验证 2 token 等效带宽翻倍，可突破上述 decode 上界，但按分析框架不属于 gap 填补（改写分母而非消除 gap）。
